# Android rigctld phase 0 audit

2026-11-20

**Recommendation**

Build an Android-only CAT APK around upstream rigctld’s command parser and the JS8Android USB bridge. Start with a single, stoppable JNI daemon and one radio. Bring up USB first, then classic Bluetooth CAT. Keep the initial APK free of modem code and audio permissions. Once CAT is stable, support shared audio over USB and compatible Bluetooth links. Evaluate Oboe/AAudio for USB PCM in both directions. Pin Hamlib streaming separately while testing the audio integration.

                                                ↕ read/write/control lines
                        Hamlib Android serial patch ↔ USB/BT JNI callbacks
                                                      ↙             ↘
                                  UsbManager + UsbSerialPort       BluetoothSocket

JS8EngineService (network mode) → RigCtlClient → existing rigctld TCP server

Proposed APK

## Running the real daemon on Android

| Approach | Tradeoff |
| --- | --- |
| **JNI with a stoppable rigctld lifecycle** | Preferred. One process lets the upstream daemon use existing bridge callbacks and Android service diagnostics. Hamlib builds the daemon and [shared parser](https://github.com/Hamlib/Hamlib/blob/1b2461aba99f0dde0531e1732c00e60aeee40657/tests/Makefile.am#L21) as program sources outside `libhamlib`. At the pin, [rigctld.c](https://github.com/Hamlib/Hamlib/blob/1b2461aba99f0dde0531e1732c00e60aeee40657/tests/rigctld.c#L246) uses process-wide CLI state, signals, exit paths, detached workers and client-dependent rig open/close. Give the daemon explicit start/stop and error return paths. Own and wake the listener, stop and join client workers, release PTT while the transport is live, then close and clean up the rig before unregistering bridge callbacks. Keep upstream parsing and command handling. Upstream the reusable lifecycle and portability changes when maintainers want them. |
| **App-packaged executable with a PTY** | Viable comparison. RADE’s [process manager](https://github.com/pepefrog1234/RADE_decode_Android/blob/238a7dafb577b4c6a03ff440653d15e3f0b9afb9/app/src/main/java/yakumo2683/RADEdecode/network/RigctldProcess.kt#L180) looks for an arm64 PIE installed as `librigctld.so` in `nativeLibraryDir`; it enables legacy native-library extraction and its native fork/exec path takes a PTY slave. The [PTY implementation](https://github.com/pepefrog1234/RADE_decode_Android/blob/238a7dafb577b4c6a03ff440653d15e3f0b9afb9/app/src/main/cpp/icom_pty.c#L40) holds the slave open across termios operations. This keeps the daemon process isolated but adds child supervision, a byte bridge, packaging dependencies and explicit handling for real modem-control lines. Android restricts execution from writable app home directories for modern targets. Qualify launch, line control and cleanup on the target phone before adopting it. [Android executable restrictions](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission) |
| **Client to an existing rigctld** | Useful for comparison and reproductions. A daemon on an external host leaves hardware ownership there. The shared parser has no supported drop-in Android service entry point at either inspected revision. |

The service should own permissions and start/stop state on Android. Start the CAT foreground service from the app with the applicable `connectedDevice` type and permissions, grant USB access or Bluetooth permission as required, and declare `INTERNET` for sockets. Bind explicitly to `127.0.0.1:4532` and show bind failure. Loopback TCP is reachable by other apps with socket access. Treat companion-app trust and control of PTT as explicit MVP design questions. A dummy rig can prove connectivity before the app accepts real hardware transmit commands. [USB host](https://developer.android.com/develop/connectivity/usb/host) [Foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types)

## Current audio path and Oboe fit

```text
JS8Android RX    Android route → AudioRecord → JNI conversion → JS8 DSP
JS8Android TX    JS8 DSP / PTT gate → native Oboe callback → Android route
Proposed audio   verified Android endpoints ↔ Oboe ↔ bounded PCM queues
                                              ↔ worker ↔ Hamlib stream provider
```

- **Device selection.** [AudioDevices](Android-port/android/app/src/main/java/com/js8call/example/ui/AudioDevices.kt#L48) lists Android input devices. [JS8EngineService](Android-port/android/app/src/main/java/com/js8call/example/service/JS8EngineService.kt#L2040) infers the output by name/type/family and can fall back to the default. It stops when the selected input disappears. [JS8AudioHelper](Android-port/adapters/android/jni/kotlin/JS8AudioHelper.kt#L148) requests a preferred capture device. Oboe TX logs the requested ID and actual stream format. These paths do not establish that the requested physical RX and TX routes were active.
- **Capture and playback.** [JS8AudioHelper](Android-port/adapters/android/jni/kotlin/JS8AudioHelper.kt#L89) probes record source, rate and channel choices, sets a preferred route and attempts to disable AGC, noise suppression and echo cancellation where available. Its record loop passes PCM to JNI, where [resampling](Android-port/adapters/android/jni/js8_engine_jni.cpp#L824) uses a FIR for integer decimation and a fractional path otherwise. [Engine setup](Android-port/adapters/android/jni/js8_engine_jni.cpp#L661) explicitly disables native Oboe capture and creates Oboe output for ordinary playback. The [Oboe adapter](Android-port/adapters/android/src/audio_oboe.cpp#L200) requests low latency and exclusive mode. Its output callback takes a mutex and uses a callback-time clock reading. Its logs and lifecycle do not verify the active route or provide stream error recovery. Reuse the build pattern and routing lessons. Implement a small radio PCM adapter independent of JS8Core.
- **PTT and gain.** [Service PTT gating](Android-port/android/app/src/main/java/com/js8call/example/service/JS8EngineService.kt#L3076) closes the transmit gate when disabling PTT and waits for a successful key command when required. JNI [TX gain](Android-port/adapters/android/jni/js8_engine_jni.cpp#L703), modem delay and serial resampling settings are JS8-specific. Put radio audio calibration in the service and leave modulation, scheduling policy and waveform levels with clients. Account for output still queued at the DAC before normal unkey. On route loss, mute/discard audio and request PTT release immediately.
- **Bluetooth and special rigs.** [SCO routing](Android-port/android/app/src/main/java/com/js8call/example/service/JS8EngineService.kt#L2494) uses Android communication-device selection and a legacy SCO path. Classic CAT RFCOMM is independent of Android media/communication audio profiles. Test SCO input, output, bandwidth and concurrent CAT per rig. [QMX](Android-port/android/app/src/main/java/com/js8call/example/service/QmxCatSession.kt#L10) has direct CAT with normal Android USB audio. [(tr)uSDX](Android-port/android/app/src/main/java/com/js8call/example/service/TruSdxSerialSession.kt#L122) multiplexes CAT and PCM on serial with its own framing and TX switching. [BTECH UV-Pro](Android-port/android/app/src/main/java/com/js8call/example/service/UvProSession.kt#L22) uses vendor RFCOMM control and 32 kHz SBC audio, whose frames can key the radio. Those two serial/vendor audio routes need device adapters outside Oboe.

For the first audio prototype, select input and output independently in Android and require a verified, current external output before TX. Prefer AAudio via Oboe and qualify both exclusive and shared modes on actual USB hardware. The Oboe guide notes that OpenSL ES ignores device IDs. AAudio or a framework route that can verify the endpoint is required for RF audio. Start with silence, inspect the actual route and register route/disconnect handling before allowing audio to reach the rig. If a route cannot be verified or moves, keep the output muted until it is explicitly re-established. Measure unplug/reroute while playing into a dummy setup because callbacks and Android route notifications can race. [Oboe guide](https://github.com/google/oboe/blob/main/docs/FullGuide.md) [Android audio routing](https://developer.android.com/reference/android/media/AudioRouting)

Open at the device’s preferred rate where feasible. Report the actual API, format, rate, channels, sharing mode, burst size, buffer size, xruns and route. Transfer PCM through preallocated bounded queues. Keep allocation, locks, JNI, file/network I/O, resampling and CAT commands off the audio callbacks. Tie timestamps to audio frame positions where supported and report uncertainty when relating the device clock to UTC. Validate signal fidelity with processing off where supported, and tune buffers against xrun counts and latency under load. Measure first/last audio versus PTT, end-to-end latency and jitter (median, p95 and p99), lost frames, input/output behavior on hotplug and recovery after backgrounding. Establish acceptance thresholds with a real-time modem client and actual rigs. [Android low-latency audio](https://developer.android.com/games/sdk/oboe/low-latency-audio)

For Bluetooth audio, first retest the FX-4CR and identify the profile it actually exposes on the target phone. For HFP/SCO, request the Android communication device and verify the routed input and output after the streams start. Try Oboe/AAudio on the negotiated route and compare with `AudioRecord`/`AudioTrack` if routing or reliability requires it. For other Android audio profiles, qualify each supported direction independently. For a vendor audio protocol such as UV-Pro, use a rig-specific adapter that presents the same PCM interface to the service. Measure bandwidth, latency, jitter and loss during simultaneous CAT and audio, and verify behavior during Bluetooth disconnect, reconnect and route changes. Record the rig firmware, phone/OS, profile and validated directions in the support notes. [Android communication routing](https://developer.android.com/reference/android/media/AudioManager#setCommunicationDevice(android.media.AudioDeviceInfo)) [Android audio device types](https://developer.android.com/reference/android/media/AudioDeviceInfo)

## Hamlib streaming integration

Confirmed at the audited `master` revision:

- Hamlib advertises effective format, channel and rate capabilities from backend caps, with conversion where supported. [`rig_stream_open`](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/src/stream.c#L1169) rejects rigs without a stream-open hook. Backend hooks exist for dummy, netrigctl client forwarding and selected Icom network rigs. The [TS-590S backend](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/rigs/kenwood/ts590.c#L1733) exposes no such hooks. An FX-4CR using that CAT model will need an additional audio provider. Android USB/BT PCM is a proposed provider, independent of which CAT backend owns the rig. If adding a provider hook upstream is impractical, evaluate a wrapper/backend that delegates CAT while supplying audio caps and stream callbacks. Verify whether timestamped queues and upstream conversion can be reused without copying samples unnecessarily. Rate conversion outside native rates also depends on the build and conversion support, including the optional libsamplerate dependency. [Streaming design](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/HAMLIB_STREAMING.md) [Backend guide](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/HAMLIB_STREAMING_BACKEND_GUIDE.md)
- TCP commands negotiate the stream and return its UDP endpoint and token. Unicast RX learns its destination through subscribe/ack and maintains it with keepalive. TX sends validated UDP samples into a backend/ring buffer. The daemon tracks stream ownership by TCP client plus token and source IP on UDP, and closes owned streams on TCP disconnect. One unicast stream has one peer. Multi-client RX needs multiple backend-supported streams with bounded fan-out, or multicast where intentionally configured. Multicast and pooled RX are unnecessary for the first Android proof. Token/IP/stream ownership alone does not establish Android app identity or ownership of radio-wide PTT.
- RX propagates sample positions, capture-time anchors, metadata and discontinuities; timed TX and burst-controlled PTT depend on the capabilities advertised by the backend. With ordinary USB audio, qualify audio-clock timing and PTT delay before advertising timed transmit capabilities. App-level TX ownership must cover both sample submission and CAT/PTT commands. Define starvation, disconnect, stale audio and timeout handling before enabling real TX.
- The [unicast UDP socket helper](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/tests/rigctld_stream.c#L523) binds the IPv6 wildcard and attempts dual stack. A TCP loopback bind alone therefore leaves a UDP socket bound across interfaces. Pass a local bind address or adapt the helper and verify both TCP and UDP sockets when bringing streaming to the APK. The wire protocol remains under development. Match client and daemon pins in tests.
- The source includes [stream API](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/test/test_stream_api.c), [rigctld streaming](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/test/test_rigctld_stream.c), [netrigctl client](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/test/test_netrigctl_stream.c), and [Icom network](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/test/test_icom_network_stream.c) suites. The dummy backend supplies simulated PCM/IQ and timing for host and Android protocol checks. The files were reviewed as references and were not run.

## Extraction and licensing

Create a small Android app module, native daemon/JNI under its native source directory, and a pinned Hamlib dependency with tracked patches and reproducible build steps. Start with the USB catalog, permission helper, bridge and JNI counterpart, the applicable Hamlib patches, and upstream daemon/parser sources. Add Bluetooth bridge/catalog as the next transport. Use the JS8 rig catalog as a reference for model enumeration. Exclude JS8Core, FFTW, Eigen, Boost, Qt, JS8 UI/DSP and special rig sessions from the CAT MVP. Keep transport diagnostics and registration independent of the UI so a contributor can test a single failure with a fake transport. Rebase the Hamlib patch series in a dedicated change when needed, and validate dummy plus USB/BT before switching the baseline. Send generally reusable lifecycle/backend hooks to Hamlib when authorized, and maintain app permissions, routing, and Kotlin USB/Bluetooth code here.

The JS8Android root carries GPLv3. Hamlib [LICENSE](https://github.com/Hamlib/Hamlib/blob/af198ace7697c84f5d8ce084271208e383012792/LICENSE) covers the library under LGPL-2.1-or-later and the rigctld program headers specify GPL-2.0-or-later. Oboe is Apache-2.0. The upstream usb-serial-for-android license at v3.7.3 is MIT. RADE’s root is LGPL-2.1 and the packaged rigctld has its own Hamlib program terms. For the proposed reuse, GPLv3 is the natural candidate for the combined app. Record provenance and per-file notices, retain dependency licenses, and meet the applicable source/build and static dependency distribution obligations before any APK release. Review the exact imported files before adopting a license or reusing RADE code. ## MVP and verification sequence

1. On Android arm64, prove a JNI start/stop cycle using the pinned Hamlib dummy model. Build a reproducible debug APK and start with loopback CAT. Use a standard desktop client through `adb forward tcp:14532 tcp:4532` and `rigctl -m 2 -r 127.0.0.1:14532 f`, and verify an Android client can connect directly on loopback. Check frequency/mode reads, protocol errors, port collisions, concurrent clients, disconnect, stop during command/open, and repeated starts. Run PTT protocol checks against dummy only at this step.
2. Add USB permissions and the serial shim. Use a fake transport for command bytes, partial replies, failures, permissions, unplug and stale-session tests. Then have the hardware owner run the FX-4CR CAT matrix over USB and classic Bluetooth using both Hamlib models, and a USB CAT-only check on the (tr)uSDX. Start with receive-only queries and record firmware and settings. Check JS8Android network mode on the same device with its separate audio route. Use deliberate low-power dummy-load testing if verifying real PTT transitions.
3. Provide a documented debug-build path and a user-triggered diagnostic export covering app/Hamlib commits, phone/Android version, rig settings and transport, sanitized command/error evidence, lifecycle events, and eventually actual audio route and stream counters. Pair it with a compact before/after reproduction and PR workflow. Ask hardware owners to run their own verification and help them send fixes to the layer that owns them. [Contributing](CONTRIBUTING.md)
4. After CAT, prototype USB PCM and qualify Bluetooth audio on the FX-4CR with simultaneous CAT. Use the owner’s Pixel 8a and record its actual OS and rig firmware. Compare Oboe with framework audio where needed. Prototype (tr)uSDX CAT and PCM demultiplexing on its shared USB serial port. Then prove one receive stream over a pinned Hamlib API, add fan-out only when needed, and qualify TX ownership before exposing TX streaming.

Open design decisions include how local modem clients are trusted and granted TX ownership while preserving standard CAT compatibility, and where a generic Hamlib audio-provider hook belongs. Performance, route-failover behavior and CAT/audio coexistence require hardware measurements.
